# База данных переехала с Neon на self-hosted VDS

Заменяет часть [ADR 0006](0006-hosting-vercel-neon.md), касающуюся базы данных. ADR 0006 с самого начала называл этот переезд открытым вариантом на случай проблем с доступностью или оплатой Neon из РФ — этот момент наступил, база перенесена на Postgres 16, self-hosted на VDS.

Схема (миграции Prisma) и сид (первый Администратор) перенесены на новую базу без изменений — модель данных не менялась, поменялся только хостинг. Драйвер приложения не изменился: `@prisma/adapter-pg` (Node `pg`) как и раньше, так что рантайм-код не тронут.

Особенности новой базы, важные для подключения:
- Сервер отдаёт TLS с самоподписанным сертификатом. Актуальная версия `pg`
  трактует `sslmode=require` как `verify-full` и требует доверенный CA —
  падает с `self-signed certificate`. Оба URL в `.env` используют
  `uselibpqcompat=true`, который возвращает `require` к обычной семантике
  libpq (шифрование без проверки CA) — это осознанный компромисс, приемлемый
  для текущего масштаба (одна школа), но его стоит пересмотреть, если
  понадобится доступ извне доверенной сети.
- На той же машине есть PgBouncer на порту `6432`. Через него ходит
  приложение (`DATABASE_URL`) и сид; напрямую в Postgres на `5432`
  (`DIRECT_URL`) — только `prisma migrate`/`db push`, поскольку схема-движок
  Prisma и PgBouncer в паре не работают надёжно (транзакционный пулинг ломает
  часть операций схема-движка). Разделение задано в `prisma.config.ts`
  (CLI берёт `DIRECT_URL`) и в коде приложения/сида (берут `DATABASE_URL`
  напрямую из `process.env`/`env.DATABASE_URL`).
- Ранее задокументированная проблема несовместимости Rust-движка Prisma (`schema-engine-windows.exe`) с TLS-хендшейком Neon (см. историю ADR 0006/README) на новой базе не воспроизводится — `prisma migrate deploy` отрабатывает штатно, отдельный ручной процесс применения миграций (описанный там же) больше не нужен.

Приложения (лендинг, админка) остаются на Vercel — риск ADR 0006 про иностранный хостинг снят только для базы, не целиком.
